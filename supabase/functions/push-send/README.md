# Push worker (Phase 6)

Delivery is disabled by default in both the database (`push_delivery_config.enabled = false`) and worker (`PUSH_DELIVERY_ENABLED` absent). No webhook or schedule is installed by the migration. Installing this code does not send push.

After explicit deployment authorization, deploy this function with JWT verification disabled **only** for this function; it requires a separate high-entropy `PUSH_WEBHOOK_SECRET` in the `x-push-webhook-secret` header. Keep this secret and `SUPABASE_SERVICE_ROLE_KEY` server-only. Set `EXPO_PUSH_ACCESS_TOKEN` if enhanced Expo push security is enabled. Set `PUSH_DELIVERY_ENABLED=true` and enable the singleton database row only when authorized to start delivery.

Configure a notification INSERT webhook to POST its standard record body here, with the secret header. The function reads only `record.id`; recipient, type, access and token are always reloaded from the database. Clients cannot insert notifications or change notification content. Authorized types are assignment, review requested, approval, rejection, comments and reopening. Push text is generic; no snag title, comment, project, user or private photo data leaves the backend.

A secure scheduled worker must POST `{ "action": "receipts" }` about every 15 minutes. This checks up to 100 due tickets, removes tokens on DeviceNotRegistered and records delivery outcomes. Reinvoke with `{ "notificationId": "..." }` for explicit transient HTTP/rate-limit retries, after the database backoff. Retry candidates are `push_deliveries.status = 'retry' and next_attempt_at <= now()`; a schedule can select these IDs server-side. Claims serialize concurrent webhook/retry invocations and stop after six attempts. Ambiguous network acceptance remains `uncertain` and is not replayed automatically because Expo does not provide an idempotency key. Stale `sending` records after worker termination likewise require operator attention; do not blindly resubmit them. Push is best effort; the persistent in-app notification is authoritative.

Native release configuration additionally needs authorized FCM v1 / APNs credentials in Expo/EAS and Android `google-services.json`. These are external configuration work, not committed credentials. Token registration is opt-in, refreshed on foreground/token rotation, expires after 24 hours without refresh and is removed on sign-out/deployment switching when online. Offline sign-out cannot revoke a token on an unreachable server; generic text and opaque deployment-bound navigation prevent private content disclosure, and taps recheck current account/project access. The next device registration transfers token ownership atomically; expired tokens are excluded. Existing in-app updates continue working without native push setup.
